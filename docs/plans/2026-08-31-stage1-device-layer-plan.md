# Stage 1 Device Layer, iOS

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Produce rally clips entirely on an iPhone - decode, inference, rally detection, cutting, sync - and measure how far the result sits from what the cloud produces for the same video.

**Architecture:** The `:analysis` module already holds every Phase 1 algorithm (see the sibling plan). What is missing is everything either side of it: a platform layer that decodes and runs models, a binary format between them, and a sync path that makes Supabase look as though the cloud had done the work. Tasks are ordered by **verifiability, not by dependency**: Part A is pure Kotlin that CI can prove today, Part B builds the fixtures that let a two-language implementation be checked, Part C is the iOS layer that needs a device. That ordering is deliberate and should not be "corrected" back into the design doc's narrative order - it front-loads everything that can fail cheaply.

**Tech Stack:** Kotlin Multiplatform (2.3.20), Swift 5.9 / iOS 17, ONNX Runtime (objc/Swift package), AVFoundation (AVAssetReader, AVAssetWriter), kotlin.test + kotest assertions, XCTest, Python 3.11 with OpenCV/PyTorch for reference runs.

**Spec:** `docs/plans/2026-08-31-on-device-analysis-pipeline-design.md`

**Predecessor:** `docs/plans/2026-08-31-on-device-gates-and-analysis-port-plan.md` - Tasks 6 to 15 of that plan are complete; the `:analysis` module exists with 68 passing tests. Tasks 1 to 5 of it, the Stage 0 gates, are **not** complete and gate Part C of this plan.

## A correction to the spec, found while writing this plan

§5.4 says "One decode pass, not three", and gives seeking as the reason: "Seeking per frame tens of thousands of times is pathologically slow on both platforms."

That reasoning is right but the conclusion is too strong. Production's TrackNet path is three sequential steps, not one (`inference.py:157-172`), and step 1 is a **median background computed from up to 300 frames sampled evenly across the whole video** (`max_bg_samples: int = 300`, `inference.py:111`; `np.linspace` sampling, `inference.py:200-201`), each reached by `cap.set(CAP_PROP_POS_FRAMES, idx)` - a seek. That background is an input to the very first inference of the main pass, so it cannot be computed lazily as the main pass goes.

The accurate statement, which this plan builds to: **one bounded seek pre-pass of at most 300 frames, then one sequential frame-by-frame decode pass.** 300 seeks is not what §5.4 objects to. Task 11 implements it this way. Update §5.4 when this plan is executed.

## Task 2: The `RawInference` binary format

§5.2. The device writes this, `:analysis` reads it, and it never leaves the phone. Roughly 5.5M floats for a 30-minute match, which is why it is binary rather than JSON (ref §2).

**Scope note:** Stage 1 is Phase 1 only - TrackNet and the detector, per §9. Pose is Stage 3. The format therefore **carries** a person record with 17 keypoints but Stage 1 writes zero of them. Design the record stream so adding them later is not a version bump: a per-frame count of zero costs four bytes.

**Files:**
- Create: `analysis/src/commonMain/kotlin/com/badmintontracker/analysis/raw/RawInference.kt`
- Create: `analysis/src/commonMain/kotlin/com/badmintontracker/analysis/raw/RawInferenceCodec.kt`
- Create: `analysis/src/commonTest/kotlin/com/badmintontracker/analysis/raw/RawInferenceCodecTest.kt`

**Interfaces:**
- Consumes: nothing
- Produces:
  - `data class RawHeader(val version: Int, val fps: Double, val totalFrames: Int, val videoWidth: Int, val videoHeight: Int, val modelVersion: String)`
  - `data class RawShuttle(val x: Float, val y: Float, val confidence: Float, val visible: Boolean)`
  - `data class RawBox(val classId: Int, val confidence: Float, val x1: Float, val y1: Float, val x2: Float, val y2: Float)`
  - `data class RawPerson(val box: RawBox, val keypoints: List<RawKeypoint>)` and `data class RawKeypoint(val x: Float, val y: Float, val confidence: Float)`
  - `data class RawFrame(val frame: Int, val timestamp: Double, val shuttle: RawShuttle?, val boxes: List<RawBox>, val persons: List<RawPerson>)`
  - `data class RawInference(val header: RawHeader, val frames: List<RawFrame>)`
  - `object RawInferenceCodec { fun encode(inference: RawInference): ByteArray; fun decode(bytes: ByteArray): RawInference }`

**Format**, fixed and little-endian throughout:

| Field | Type | Notes |
|---|---|---|
| magic | 4 bytes | ASCII `RAWI` |
| version | int32 | `1` |
| fps | float64 | |
| totalFrames | int32 | frames declared, not necessarily present |
| videoWidth, videoHeight | int32, int32 | source pixels, not model input size |
| modelVersion length + bytes | int32 + UTF-8 | stamps which weights produced this |
| frameCount | int32 | records that follow |
| per frame | | `frame` int32, `timestamp` float64, `shuttleFlag` int8, then shuttle if flagged, `boxCount` int32 then boxes, `personCount` int32 then persons |

Coordinates are in **source-video pixels**, already scaled back from model input size the way `inference.py:154-155` does with `w_scale = orig_w / WIDTH` and `h_scale = orig_h / HEIGHT`. Putting model-space coordinates in this file would push a scaling responsibility across the boundary that §5.1 says belongs to the platform layer.

- [x] **Step 1: Write the failing tests**

`RawInferenceCodecTest` must prove:
1. **Round trip.** A `RawInference` with two frames - one carrying a shuttle and two boxes, one carrying neither - encodes and decodes to an equal value. Use distinct non-round values in every numeric field (for example `x = 123.45f`, `timestamp = 1.0 / 3.0`) so a field-order swap cannot pass.
2. **Endianness is pinned.** Encode a header with `totalFrames = 1`, and assert the four bytes at the known offset are `01 00 00 00`. Without this the format is only self-consistent, and the Swift writer in Task 14 is the other half of the pair.
3. **The magic and version are checked on decode.** Corrupt the magic, and decoding must fail with a message naming the file as not a `RawInference`. Bump the version byte to `2`, and decoding must fail naming the version. A truncated stream must fail rather than return a short frame list.
4. **Absent shuttle survives.** A frame with `shuttle = null` decodes back to null, distinct from a frame with a shuttle whose `visible` is false. Those two mean different things: no model output at all, versus a model output that resolved to no blob.
5. **A zero-person frame is one int32.** Assert the encoded size of a frame with no persons equals the header-independent size you compute by hand. This is the assertion that keeps Stage 3 from needing a format version bump.

- [x] **Step 2: Run the tests to verify they fail**

Run: `./gradlew :analysis:jvmTest --tests "*RawInferenceCodecTest*"`
Expected: compilation failure.

- [x] **Step 3: Implement the codec**

Kotlin multiplatform has no `ByteBuffer`. Write the byte handling by hand over a `ByteArray`; both targets must produce identical bytes, so do not reach for a platform-specific buffer type through `expect`/`actual`.

- [x] **Step 4: Run the tests**

Run: `./gradlew :analysis:jvmTest :analysis:iosSimulatorArm64Test`
Expected: PASS on both. The iOS target matters here specifically: this is the format Swift will write.

- [x] **Step 5: Commit**

```bash
git add analysis/src/commonMain/kotlin/com/badmintontracker/analysis/raw analysis/src/commonTest/kotlin/com/badmintontracker/analysis/raw
git commit -m "feat: RawInference binary format with reader and writer"
```

## Task 5: Clip-boundary drift and annotation re-anchoring

§5.4's last paragraph, and the one place local deliberately does something the cloud does not. New weights produce a different `RawInference`, hence different clip bounds, hence annotation timestamps pointing into footage that has moved - ref §8.5's bug arriving by a new route.

The rule, verbatim from §5.4: when a re-analysis moves a clip's bounds beyond a small epsilon, every annotation on that clip has its `timestamp_seconds` shifted by the boundary delta, in the same transaction that writes the new bounds. Annotations that would fall outside the new clip are flagged rather than silently clamped.

**Files:**
- Create: `shared/src/commonMain/kotlin/com/badmintontracker/shared/local/ClipReanchoring.kt`
- Create: `shared/src/commonTest/kotlin/com/badmintontracker/shared/local/ClipReanchoringTest.kt`

**Interfaces:**
- Consumes: `ClipWindow` from `:analysis`
- Produces:
  - `data class Reanchored(val annotationId: String, val newTimestampSeconds: Double, val outsideNewClip: Boolean)`
  - `data class ReanchorPlan(val shiftSeconds: Double, val moved: List<Reanchored>, val flagged: List<Reanchored>)`
  - `fun planReanchor(oldStart: Double, newStart: Double, newDuration: Double, annotations: List<Pair<String, Double>>, epsilonSeconds: Double = 0.05): ReanchorPlan?`

Returning null means the boundary did not move beyond epsilon and nothing should be written. `0.05` matches the neighbour-clamp guard already used in `refineRallies`.

- [x] **Step 1: Write the failing tests**

`ClipReanchoringTest` must prove:
1. **A sub-epsilon move is a no-op:** a 0.01s shift returns null, so no transaction is opened and no rows are touched.
2. **A real shift moves every annotation by the boundary delta.** Clip start moves from 10.0 to 8.5; an annotation at 2.0 seconds into the clip becomes 3.5. Assert the exact value: annotation timestamps are relative to clip start, so the delta is `oldStart - newStart` and getting the sign wrong is a silent, plausible failure that moves every annotation the wrong way.
3. **The sign is pinned in both directions.** Repeat with the clip start moving later, 10.0 to 11.5, and assert the annotation at 2.0 becomes 0.5.
4. **An annotation pushed before the new clip start is flagged, not clamped.** An annotation at 0.5 with the start moving 10.0 to 11.5 lands at -1.0; it must appear in `flagged` with `outsideNewClip` true and its computed timestamp preserved, never coerced to 0.0. Clamping is what silently corrupts a coach's notes.
5. **An annotation past the new clip end is flagged the same way.**
6. **`moved` and `flagged` partition the input** - assert their sizes sum to the input size, so nothing is dropped.

- [x] **Step 2: Run to verify failure**

Run: `./gradlew :shared:jvmTest --tests "*ClipReanchoringTest*"`

- [x] **Step 3: Implement**

Pure computation, no repository calls. The transaction that applies it belongs to Task 16; keeping the arithmetic separate is what makes these cases testable without Supabase.

## Task 8: The shuttle-postprocessing golden vector

**BLOCKED:** needs TrackNet weights and a source `.mp4`.

This is the load-bearing artifact of the whole design. §5.4 accepts a two-language implementation of the heatmap postprocessing - the one place it does - and buys it with "a shared golden vector: a committed fixture of model outputs and their expected coordinates that both the Swift and the Kotlin implementations must reproduce, plus a Python reference run from the production code itself."

Without this fixture, Tasks 9 and 13 are two independent guesses at the same algorithm, which is precisely the duplication this design exists to avoid.

**The algorithm to pin**, from `_heatmap_to_coord` at `inference.py:477-505`, verified by reading:
- threshold at `0.5`, `max_area = 100` (both are default parameters at `inference.py:477-478`)
- empty binary mask returns not visible
- `cv2.connectedComponentsWithStats` on the thresholded mask
- **blobs with area strictly greater than `max_area` are skipped**, then the largest of those remaining wins
- if none survive, returns not visible - a behaviour argmax cannot express
- the coordinate is the heatmap-weighted centroid of the winning blob's pixels, so it is sub-pixel

And the median background, from `_compute_median_background` at `inference.py:193-220`:
- `min(total_frames, max_samples)` frames, `max_samples` defaulting to `300` (`inference.py:111`)
- indices from `np.linspace(0, total_frames - 1, sample_count, dtype=int)` then `np.unique`
- each sampled frame resized to 512x288 and converted BGR to RGB
- pixel-wise `np.median` over the stack, then `.astype(np.uint8)` - a truncation, not a round

**Files:**
- Create: `tools/models/make_shuttle_vectors.py`
- Create: `analysis/src/commonTest/resources/shuttle/heatmaps.bin`, `expected.json`, `README.md`
- Create: `analysis/src/commonTest/resources/shuttle/background.json`

**Fixture format**, chosen so both Kotlin and Swift can read it without a JSON float-precision argument:
- `heatmaps.bin`: int32 count, then per case an int32 width, int32 height, and `width * height` float32 values.
- `expected.json`: per case, `{"index": n, "visible": bool, "x": float, "y": float}` with x and y in model space at 512x288, not source pixels.
- `background.json`: a small set of sampled 8-bit frames and their expected pixel-wise median, to pin the truncation.

**Cases the fixture must include**, chosen because each one distinguishes the real algorithm from a plausible wrong one:
1. A single clean blob - the ordinary case.
2. A blob of area exactly `100` - must be **kept**, since the rejection is `area > max_area`.
3. A blob of area `101` - must be **rejected**.
4. A frame whose only blob is oversized - must return **not visible**. An argmax implementation returns a coordinate here, so this case alone catches the most likely wrong implementation.
5. Two blobs where the larger is oversized and the smaller is not - the smaller must win, not the larger.
6. Two valid blobs of different areas - the larger must win.
7. An all-zero heatmap - not visible.
8. A blob whose weighted centroid differs measurably from its geometric centroid, proving the weighting is applied.

- [ ] **Step 1: Write the generator**

`make_shuttle_vectors.py` imports `_heatmap_to_coord` from the production module - do not reimplement it - runs it over both real heatmaps captured from a TrackNet run and the synthetic cases above, and writes the three fixture files.

Real heatmaps and synthetic cases both: the synthetic ones pin the branch behaviour precisely, the real ones prove the branches are reachable with actual model output.

- [ ] **Step 2: Generate and commit the fixture**

Keep it small enough to commit. At 512x288 float32 a single heatmap is 590KB, so store the synthetic cases at a reduced size and no more than four real ones.

- [ ] **Step 3: Record provenance**

`README.md` beside the fixture states which video, which weights SHA from `tools/models/manifest.json`, and the exact command. A golden vector whose origin is unrecorded cannot be regenerated when a model changes, and becomes unfalsifiable.

Record **`total_frames` and the trim window** as well, not just the video name. `_compute_median_background` samples with `np.linspace(0, total_frames - 1, ...)`, so the sampled indices - and therefore the background, and therefore every heatmap in the fixture - depend on the frame count of the exact clip used. Regenerating from a differently-trimmed cut of the same source silently produces different vectors, and the Swift and Kotlin implementations would then be checked against a fixture nobody can reproduce.

- [ ] **Step 4: Commit**

# Part C: the Android device layer

**Android first, not iOS.** The design's section 9 puts iOS first, on the
grounds that its hardware range is narrower and the signal cleaner. That
reasoning still holds in the abstract, but there is no iPhone available and
there is a Galaxy S23, and a device you can run on beats a cleaner signal you
cannot measure.

It also turns out to be the better first target on the merits, which is worth
stating so this is not read as settling:

- **`androidApp` is Kotlin, so `:analysis` runs on the device unchanged.** It
  already depends on `:shared`, which now re-exports `:analysis` through
  `api(project(":analysis"))`. `RawInferenceCodec` and the heatmap
  postprocessing are used directly rather than reimplemented.
- **That removes the one two-language implementation the design accepted.**
  Section 5.4 concedes a Swift and Kotlin pair for the heatmap blob detection
  and buys it with a shared golden vector. On Android there is no pair: the
  Kotlin from Task 9 is what runs. The former Task 13 is deleted outright, and
  Task 8's fixture stays only as the check that the single implementation
  matches production's Python.
- **The `RawInference` writer is the reader.** No second byte-level
  implementation, so the endianness contract has one side rather than two.

iOS becomes the later stage, and it inherits a device layer whose interface
has already been exercised against a real engine rather than only a fake -
which is a better position than the plan started from.

**BLOCKED** on the 0a gate having passed. Everything else it needed is in
place: the weights are pulled and pinned, TrackNet and InpaintNet are exported

## What comes next, and why it is not in this plan

**Stage 2, Android.** Only the platform layer is new. Deliberately after iOS: §9 puts iOS first because its hardware range is narrower and the signal is cleaner, and doing both at once would mean debugging two decoders against an unproven `RawInference` contract.

**Stage 3, Phase 2.** Pose, identity, speed and distance, the derived analytics. §9 calls it the largest stage and says stage 0b decides its shape - and 0b has not been run.

**Stage 4, capability routing.** The §5.6 threshold "cannot be set from source and comes from §7's stage 0b". Writing routing tasks now would mean inventing the number the measurement exists to produce.

**Stage 5, hardening.** Interruption and resume, thermal backoff, intermediate storage, the iOS background-execution question from ref §11.6.
